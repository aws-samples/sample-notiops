# 成本突增排查

你正在执行一次**只读**的成本根因调查。你要说清*发生了什么变化*以及
*为什么*，所有结论完全以 Cost Explorer 数据为依据。你不修改任何资源。

## 何时使用
- 「我的账单涨了」「成本突增」「成本异常」「为什么这个月比上个月更贵」
  「支出高于预期」。

## 步骤

1. **确认对比窗口。** 明确要对比的两个周期（例如本月对比上月，或异常那一周
   对比前一周）。若不明确，默认采用当前月对比上一月，并说明这一点。
2. **按服务的顶层差异。** 拉取两个周期按服务分组的未混合成本（unblended cost）。
   计算各服务的差异并按绝对增量排序——这一步通常一步就能点出
   罪魁服务。
3. **下钻分析涨幅最大的项。** 针对增量最大的服务，跨两个周期按
   **用量类型（usage type）**（相关时也按**区域（region）**）分组，看清究竟是哪个维度
   在增长（例如 NAT gateway 数据处理、跨 AZ 传输、存储的 GB-months、
   某个特定实例族的实例小时数）。
4. **检查异常。** 如果有成本异常检测工具可用，拉取近期异常以作佐证，
   并捕捉那些被周期对比平滑掉的突增。
5. **尽可能归因。** 如果该账号是付款账号（payer），按关联账号（linked account）分组，指出
   是哪个账号在增长。注意资源级归因可能需要 CUR/Athena。

## 报告格式

以关键结论开头：**「增加 $X（+Y%），主要由 <service> / <usage type> 驱动。」**
然后：

| 排名 | 服务 | 上期 | 本期 | Δ | Δ% | 可能诱因 |
|---|---|---|---|---|---|---|

接着给出一段简短的**根因叙述**（2-4 句）和**下一步建议**（需要验证什么、
Savings Plan 或右调规格（right-sizing）是否有帮助、若看起来像意外扣费则提议开一个 Support case）。
并提议保存完整报告。

## 护栏
- 只读。每个数字都来自 Cost Explorer 的输出，并标明所属周期。
- 区分真实的用量增长与定价/抵扣额度到期——当差异看起来像折扣到期
  而非新增用量时，要明确指出。
- 如果某个周期的数据不完整（当前月尚未结账），要说明当前月的数字
  是部分/运行速率（run-rate）值，而非最终值。
