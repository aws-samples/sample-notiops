# RDS 运行健康检查

你正在对一个或多个数据库执行**只读**的 RDS 最佳实践检查。
每一条结论都必须以工具返回的配置或指标为依据——不得凭空假设。

## 适用场景
- 用户询问 RDS 健康度、可靠性、"这个数据库是否存在风险"、最佳实践，
  或某个具体的 RDS 性能 / 可用性问题。

## 步骤

1. **清点。** 列出（相关区域内的）RDS 实例。若用户指定了某个实例，则聚焦
   该实例；否则检查其中值得关注的实例。
2. **逐个数据库描述配置**并检查：
   - **Multi-AZ**：单可用区的生产数据库存在弹性风险 → HIGH。
   - **备份**：已启用自动备份且保留期 ≥ 7 天；具备 PITR 能力。
   - **删除保护**：生产环境应开启。
   - **公网可访问性**：可公网访问的数据库属于安全问题 → HIGH。
   - **加密**：已启用存储加密。
   - **引擎版本**：标记临近或已过 end-of-support 的版本。
3. **指标（近 24h-7d）：** CPU utilization、freeable memory、free storage space、
   database connections、读/写延迟。据此判断：
   - **存储余量**：可用空间持续趋近于零 → HIGH（存在中断风险）。
   - **规格评估**：CPU 持续极低 + 连接数很少 → 规格过大（成本浪费）；CPU / 延迟
     持续偏高 → 规格不足（性能瓶颈）。
4. **近期事件与待执行维护：** 拉取近期的 RDS 事件（故障切换、存储自动扩容、
   重启）以及任何待执行的维护操作。

## 报告格式

为每个数据库给出总体评级和一张问题表：

| 严重程度 | 问题 | 依据 | 建议 |
|---|---|---|---|
| CRITICAL / HIGH / MEDIUM / LOW | … | 工具返回的指标/配置 | … |

严重程度参考：**CRITICAL** = 即将发生的中断/数据丢失风险（存储接近写满、
生产环境无备份）。**HIGH** = 单可用区生产、可公网访问、EOL 引擎。**MEDIUM** =
规格评估、保留期 < 7 天。**LOW** = 无关紧要/仅供参考。

结尾给出最重要的 3 项行动，并主动提出可保存完整报告。

## 防护红线
- 只读：仅描述与建议；绝不修改任何数据库。
- 每一条严重程度判定都要引用其所依据的具体指标或配置字段。
- 若该时间窗内指标不可用，如实说明，而不要臆断数据库一切正常。
